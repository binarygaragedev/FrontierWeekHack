# Challenge 2: Monitor with Application Insights

## Objectives

By the end of this challenge, following item will be completed:

- ✅ Tracing enabled for the ride-hailing safety agents
- ✅ Agent calls captured in Application Insights
- ✅ Live risk contracts verified in traces (event source vs final risk-state owner)
- ✅ A basic understanding of how to debug and improve AI agent behavior in production

## Context

Monitoring is essential for ride-hailing AI because a bad safety decision is not just a product issue — it can directly affect passenger and driver trust, operational risk, and compliance.

Without observability, you cannot tell:

- whether the agent actually called the relevant safety tools,
- whether the model used the right trip data,
- whether a trip was escalated correctly,
- whether the model responded too aggressively or too conservatively.

## Why monitoring matters

Ride-hailing systems need monitoring in three ways:

1. Reliability — confirm that the agent call succeeds and returns a usable result
2. Performance — track latency and token usage over time
3. Debugging — inspect why a trip was classified as normal, warning, or critical

## Monitoring setup

This script loads the environment from the root `.env` file, enables Azure Monitor tracing, and then runs a trip safety check through the Foundry agent API.

## Contract model verified in this step

This monitoring step enforces the live-agent contract used in the solution design:

- Telemetry Agent responsibility: emit event-level driving anomalies and severity.
- In-Trip Monitoring responsibility: own the authoritative `final_live_risk_state` and escalation action.
- Conflict rule: if telemetry severity and route context disagree, In-Trip Monitoring applies policy thresholds and can set `review_required`.

Timing model:

- Pre-trip approval is out of scope for this monitor script.
- The traced scenario starts only after departure (`lifecycle_phase=in_trip`).

## Step 1: Run the monitoring script

From the `ridehailing-solution` root:

```bash
cd challenge-2-monitor
run-monitor.cmd
```

Fallback option:

```bash
cd challenge-2-monitor
python monitor.py
```

This script will:

- enable tracing,
- create an in-trip monitoring decision agent,
- run an in-trip risk consolidation test,
- and print the result.

## What to look for in Application Insights

After the script runs, check Azure Portal:

- Application Insights → Search
- look for the trace generated by the ride safety agent
- inspect the model call, tool call, latency, and completion content
- confirm `source=telemetry_agent` appears in tool output and `state_owner=in_trip_monitoring_agent` appears in the final decision

## Example data being traced

The monitored agent evaluates an in-trip example such as:

- trip ID: `RIDE-103`
- lifecycle phase: `in_trip`
- telemetry events: hard brake, speeding, rapid acceleration
- route context: route deviation and idle duration
- expected final live risk state: `critical`

The trace should show the full path from:

- user input,
- model reasoning,
- tool invocation,
- returned telemetry and route payload,
- final live risk state and escalation action.
